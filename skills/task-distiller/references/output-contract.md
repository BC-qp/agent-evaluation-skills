# 任务包输出合同

一次完整运行产出一个提纯任务包目录（默认写到用户指定位置；未指定时写到当前工作目录下的 `distilled_task/`）：

```text
<output>/
├── prompt.md                # 统一任务提示词（可原样交给任何待测模型）
├── design_notes.md          # 任务设计说明（保留的真实难点、开放的决策空间、粒度取舍）
├── desensitization_log.md   # 脱敏与假设记录（只记类别、代号和判断，不写原值）
├── acceptance_checklist.md  # 可执行的验收清单或验收方法
└── risks_and_gaps.md        # 风险、缺失信息、不确定项
```

只有 `prompt.md` 和完成任务所必需的脱敏输入可以交给执行者。`design_notes.md`、
`desensitization_log.md`、`acceptance_checklist.md`、`risks_and_gaps.md` 仅供任务设计者、
验收者或个人复盘使用，不得与执行提示词一起提供，以免泄露设计意图、验收重点或敏感处理记录。

当材料不适合生产化时，不写 `prompt.md`，改写 `rejection.md`，包含：拒绝原因、属于哪类不足、最小补充建议、补全后如何重新触发。

### prompt.md 的固定结构

下列为基本信息结构，章节可合理合并并保留其含义。高复杂度开发题或用户要求沿用分维度编号格式时，按需读取[高复杂度开发任务提示词模板](../assets/development-prompt-template.md)：需求用维度标题组织，维度下用“1、2、3……”拆独立功能点；先校准真实输入、业务联动及批处理可压缩的部分，再取舍维度，不固定模块数，也不把具体旧题业务写成通用要求。

```markdown
# 任务：<一句话目标>

## 背景
<脱敏后的真实业务上下文，只保留完成任务所需信息>

## 输入材料
<相对路径或内嵌材料；使用约定的只读输入副本>

## 你的任务
<目标、边界、必要约束；不要写逐步答案>

## 交付物
<可打开、可运行或可人工核查的产物清单与格式>

## 验收标准
<硬门槛 + 质量核查方法>

## 护栏
<高风险/不可逆操作的限制；失败时最低要保存什么>

## 完成说明
<不得伪造工具、过程记录、截图或未验证结论；遇到阻塞时如实说明已完成部分与证据缺口>
```

### design_notes.md 必须回答

- 保留了哪些真实业务难点和决策点，为什么它们能区分模型能力；
- 哪些方案/工具/取舍被刻意留空；
- 为什么这个任务既不过宽也不过死；
- 提示词中**不包含**标准答案或隐藏解法的声明。

设计说明不得泄露标准答案，不得按模型名称提供差异化提示。

真实值映射如果确有内部复核需要，单独存放在授权的私有位置，不放入可分享任务包；不在公开说明里列出已删除的真实名称。
